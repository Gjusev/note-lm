# T1 report — Docling vs current extractor (pdf-parse)

Date: 2026-09-29. Evaluation scaffolding only, under `eval/docling-proto/`; nothing
committed. Criteria were fixed in [t1-criteria.md](t1-criteria.md) **before** any
measurement (strategy §10: thresholds are set before the run; mandate T1 row:
"Mejora de extracción y anclaje en clases definidas, con tiempo/RAM/tamaño de
paquete documentados; ninguna región inventada").

## Verdict

**DEFER** — driven by the hard gate **C8 (managed runtime)**: measured
venv + weights = 1406.6 MB + 729.8 MB = **2136.4 MB > 2048 MB** (miss by
88.4 MB). Under the pre-written rule (C8 is hard: "Rechazar un adaptador si
incumple el instalador autónomo o presupuestos acordados"), this alone forces
defer regardless of quality. Independently, **C2 (reading order) failed** —
Docling did not recover strict column order on the two-column fixtures and
performed **no better than pdf-parse** there — so a quality-only adoption was
never on the table either; TC would have been scoped out and the remainder
would still have hit the C8 hard gate.

## Setup (exact)

- Python 3.12.2 (`C:\Python312\python.exe`), venv at `eval/docling-proto/.venv`.
- **docling==2.131.0** (docling-core 2.99.0, docling-ibm-models 4.0.3,
  docling-parse 7.22.1), torch 2.14.0+cpu, rapidocr 3.9.2, reportlab 5.0.1,
  img2pdf 0.6.3, pypdf 6.19.0; full lock in `requirements.lock.txt`.
- Pipeline (recorded exactly in every `results/docling_results_run*.json`):
  `PdfPipelineOptions` with `do_ocr=True`, `do_table_structure=True`,
  `do_cell_matching=True`, **OCR backend pinned to `RapidOcrOptions`**
  (mode=default, lang=['ch'], scale=3.0, onnxruntime, force_full_page_ocr=False).
  Pinning was deliberate: this dev machine has tesseract on PATH, so Docling's
  default `OcrAutoOptions` would silently have selected a user-side system
  binary — a C8 violation by accident of the eval machine.
- Models pre-fetched via `docling.utils.model_downloader` into
  `eval/docling-proto/docling_models/` (729.8 MB): layout heron torch 163.8 MB
  + **heron onnx 163.3 MB (the variant the runtime loads)** + tableformer
  snapshot 341.6 MB + RapidOCR PP-OCRv6 61.0 MB.
- pdf-parse 2.4.5 from the repo `node_modules` (same import style as
  `eval/corpus/document-trees-v1/validate-corpus.mjs`), per-page text via
  `getText()`.

## Corpus (deterministic, verified)

8 synthetic-authored PDFs (2–6 pp), generated by
`corpus/generate_corpus.py` (reportlab `invariant=1`, fixed fonts, no RNG).
Generated twice and byte-compared: **all files identical** (evidence:
`results/corpus_check/`). Pre-flight: every text-layer phrase verified present
on its expected page with pypdf; scan-like doc verified to have **no text
layer**. Classes: 2 single-column, 2 two-column (print-style justified
columns, content stream line-interleaved), 2 ruled tables with numbers/units,
1 image-only scan-like, 1 mixed (text page + table page + image-only page).

What pdf-parse loses (the honest baseline): scan pages come back **completely
empty** (0/11 expected phrases, no OCR), the mixed doc's image page comes back
empty, table **structure** is irrecoverable (0/3 tables, 0/73 cells with
position; row text survives as flat text at 92.9%), and reading order is
whatever the content stream / geometric line builder yields. Docling keeps all
of that (73/73 table cells positionally, SN 100% OCR recall) with **zero
invented regions** — every provenance bbox inside its page rect, every matched
quote on its expected page (C5 pass, precision 1.0, prov_missing 0).

## Why C2 failed (both tools, equally)

The two-column fixtures are print-style justified columns whose content
stream is line-interleaved. Both extractors produce the same band-interleaved
order: pdf.js (pdf-parse) because it builds lines geometrically, Docling
because its layout model merges cross-gutter bands into single text items
("WQL1 … WQR1 …"). Verified against Docling's own Markdown export — not an
artifact of my unit iteration (tokens appear `wql1, wqr1, wqr2, wql2, …`).
Docling's reading order was **never better than the baseline** on this class;
the fixture (uniform baseline grid, regular bands) may be harder for layout
models than real multi-column documents, which was **not** measured here.

## Managed-runtime feasibility (mandate §7)

The no-manual-Python rule allows packaged runtimes, so the question is pure
cost: the pinned stack needs **1.41 GB venv** (torch 501.6 MB + opencv 112 MB
+ scipy 109 MB + transformers 98.5 MB …) plus **730 MB weights** as downloaded
by the standard docling downloader = 2.14 GB, over the pre-agreed 2 GB budget
by 88 MB. The download contains obvious fat (both torch and onnx layout
variants; the tableformer snapshot dir is a repo snapshot) — a curated
weights set could plausibly land under budget, but that is a different
configuration than the one measured, and the criteria are mechanical. OCR
backend: RapidOCR is pip-only (no system binary) — the only hard C8 sub-rule
that is unambiguous. Cold start 5.99 s and warm 2.27 s/doc fit the timing
sub-rules comfortably.

## Fixture corrections after first measurement (full transparency)

Criteria were never changed. Three harness defects were found by the first
run and fixed before accepting results:

1. Scan-like pages carried a text footer (a real fixture bug — image-only
   pages must have no text operators). Fixed; re-verified no text layer.
2. The grader filtered table units on `kind == "table"` while the runner
   emits `"TableItem"` — Docling's tables were correct; my grader missed
   them. Fixed.
3. The TC fixture initially drew ragged columns with aligned baselines, then
   justified columns on a shared baseline grid — Docling merged cross-gutter
   bands in both. Kept the justified version (the realistic print layout) and
   **stopped iterating there**; further fixture tuning to chase a pass would
   be goalpost-moving.

Re-measured end-to-end (corpus regenerated + determinism re-verified +
baseline + docling run1/run2 + grade) after each fixture change.

## Limitations / not measured

- **No real-world PDFs**: 8 synthetic fixtures authored by this eval. Real
  scans, rotated pages, mixed fonts, and genuine multi-column papers
  (LaTeX/Word) are untested; C2's failure may be a fixture artifact — but the
  gate stands as pre-written on the measured fixture.
- **MX chart labels OCR 2/5**: the three bar labels next to dark filled bars
  were not OCR-recovered (SN plain-text pages scored 11/11). OCR on graphic
  regions is under-measured with n=1 chart.
- run1 "first doc" (6.03 s) excludes model download time: weights were
  pre-fetched in a separate step, so download duration was not captured.
- Single hardware profile (this Windows machine, CPU-only); no German
  benchmark PDFs, no rotated/scanned tables, no benchmark of Docling's
  streaming/cancellation behavior, no license review of shipped weights
  (strategy §3 requires separate license checks per adoption).
- Anchors graded at page + bbox-validity level. No charspan-level overlap
  test against rendered regions.
- Distribution: measured on-disk sizes of the standard downloader output;
  no installer integration, no startup-in-Tauri test (that is the packaged
  lifecycle gate beyond this eval's scope, per the PI-2 criteria pattern).
