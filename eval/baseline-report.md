## Current retrieval contract (baseline system)

Implemented in `src/lib/services/hybrid-search.ts` (`searchHybrid`):

- **FTS5/BM25 branch** (`searchChunks`) + **vector KNN branch**
  (`vectorSearch` over sqlite-vec `vec0` tables), fused with **reciprocal
  rank fusion** (`fuseRankings`, `src/lib/services/retrieval.ts`). Scores are
  never summed across branches — only ranks.
- Up to **40 candidates per branch**; final `limit` default 10.
- Notebook/source filters are applied **inside both branches** (never
  post-filtered after truncation).
- Vector branch runs only when a profile + embedder + extension exist; the
  vector status is typed `ok | indexing | failed | unavailable` and a failed
  branch degrades to `mode: "fts"` — it is never reported as a successful
  hybrid run.
- Retrieval metrics seam: `computeRetrievalMetrics` (recall@10, MRR,
  nDCG@10) in `src/__tests__/retrieval-metrics.test.ts`; eval runner
  `npm run eval:retrieval` (`scripts/eval-retrieval.ts`).

## Known limitation carried forward

The only existing retrieval evaluation is `eval/corpus/retrieval-v1.json`:
**8 single-chunk documents and 8 questions** (2 of them no-answer probes).
The plan explicitly rules this out as sole validation ("No reutilizar ocho
documentos como única validación") — it exercises the harness seam, not
document-tree behavior: no multi-page documents, no sections, no tables, no
page-level citations. The corpus below replaces it as the PI-1 comparison bed
while the old file stays for the cheap smoke run.

## PI-0 corpus and questions produced

Generated by `eval/corpus/document-trees-v1/generate-corpus.mjs`
(pdf-lib devDependency, deterministic output; run twice → byte-identical
SHA-1 for all 21 PDFs):

- **21 documents** (min. required 20), **171 pages** total, 8-9 pages each;
  languages: **en 7 / es 7 / de 7**.
- Per doc: 3-7 named sections (each section starts on a new page), title
  page, recognizable headings, and objective facts (names, dates, figures,
  tables) for gradeable answers.
- Special cases: **5 no-TOC docs** (degradation/rejection test, required ≥ 2);
  **1 table split across two pages by design** (es-delta-citricos; a second
  doc breaks a table naturally); **3 docs with deliberately misleading
  heading structure** (heading topic ≠ body topic).
- Sidecars: one JSON per PDF with per-page `sectionTitles`, `firstWords`,
  `toc` flag, `pageLabels`; plus `manifest.json` (totals, language counts,
  generator and pdf-lib versions).

Questions (`questions.json`): **80 total** — dev **30** / eval **50**.

| Type | dev | eval | total |
| --- | --- | --- | --- |
| exact-fact | 9 | 16 | 25 |
| within-doc-xref | 6 | 9 | 15 |
| cross-section-comparison | 3 | 7 | 10 |
| cross-document-comparison | 4 | 6 | 10 |
| unanswerable | 8 | 12 | 20 |

Validation (`validate-corpus.mjs`, exit 0): all **86** expectedEvidence
quotes confirmed present on their claimed PDF page via pdf-parse extraction
(whitespace-normalized), every claimed section confirmed against the sidecar
page map, all **20** unanswerable probe terms confirmed absent from the whole
corpus text, manifest/sidecar/question schema consistent. Answerable questions
span all 21 documents; 10 cross-document comparisons deliberately pair
documents of different languages (en/de, en/es, es/de).

## Deviations / notes

- `pdf-lib` added as devDependency (pure JS, no native/build step, emits
  reproducible bytes once metadata dates are pinned); `package-lock.json`
  updated accordingly. No other dependency changes.
- Page counts land at the low end of the required 8-16 range; sections are
  compact but fact-dense rather than padded.
- Corpus text is WinAnsi-encoded (standard PDF fonts); validation matches
  quotes after whitespace normalization, so line wraps inside quotes are fine.
- PI-0 scope only: no retrieval has been run against this corpus yet; PI-1
  runs FTS-only vs hybrid vs PageIndex vs hybrid+tree over these exact files.
